# 순차 탐색과 상태 유지

## 뒤에서부터 순회하며 오른쪽 최댓값 유지하기

> 정리일: 26.11.19

각 위치보다 뒤에 있는 값 중 최댓값이 필요할 때, 매번 뒤쪽 전체를 탐색하면 중복 계산이 생긴다.
길이 n에서 모든 i에 대해 j = i + 1부터 끝까지 비교하면 총 n(n - 1) / 2번이므로 O(n²)이다.
n이 100,000이면 약 50억 번의 비교가 필요하다.

오른쪽에서 왼쪽으로 이동하면 이미 확인한 구간의 최댓값 하나를 재사용할 수 있다.
현재 위치를 처리하기 직전에는 오른쪽 구간의 최댓값을 유지하고,
처리한 뒤 현재 값까지 포함하도록 갱신한다.

```java
int[] values = {9, 1, 5}; // 비어 있지 않은 배열
int rightMax = values[values.length - 1];
for (int i = values.length - 2; i >= 0; i--) {
    // 갱신 전 rightMax는 i보다 오른쪽에 있는 값들의 최댓값
    System.out.println(values[i] + "의 오른쪽 최댓값: " + rightMax);
    rightMax = Math.max(rightMax, values[i]);
}
// 1의 오른쪽 최댓값: 5
// 9의 오른쪽 최댓값: 5
```

전체 최댓값과 특정 위치 이후의 최댓값은 다르다. 위 예제의 전체 최댓값은 9지만,
값 1 이후의 최댓값은 5다. 시간 순서가 중요한 경우 이미 지난 위치의 9를 사용해서는 안 된다.
최댓값의 위치가 필요하지 않으면 인덱스 목록을 별도로 저장하지 않아도 된다.

매일 최대 한 개를 사고 나중에 보유한 물건을 제한 없이 팔 수 있으며 자금·보관 제약이나 수수료가 없다면,
각 구매일 이후의 최고 가격과 구매 가격의 양수 차이를 합산할 수 있다.
각 물건을 그 이후 최고 가격에 팔 수 있고, 같은 날 여러 개를 팔아도 서로 방해하지 않기 때문이다.
이 조건이 달라지면 같은 계산을 그대로 적용할 수 없다.

각 원소를 한 번만 처리하므로 시간은 O(n), 최댓값 유지에 드는 추가 공간은 O(1)이다.
입력을 배열에 저장하는 공간까지 포함하면 O(n)이다. 누적 합의 타입은
[큰 합계를 long으로 누적하기](../java/type-conversion.md#큰-합계를-long으로-누적하기)를 참고한다.

## 두 횟수의 관계를 차이 하나로 표현하기

> 정리일: 26.11.09 (Git 기록 기준)

두 종류의 개별 횟수가 필요하지 않고 같아지는 시점이나 두 횟수의 차이만 필요하다면
차이 하나를 저장할 수 있다.

> 정리일: 26.11.08 (Git 기록 기준)

```text
balance = 첫 번째 종류의 개수 - 두 번째 종류의 개수
```

> 정리일: 26.11.08 (Git 기록 기준) · 보강일: 26.11.09 (Git 기록 기준)

첫 번째 종류를 읽으면 1을 더하고, 두 번째 종류를 읽으면 1을 뺀다.
`balance == 0`이면 두 횟수가 같다. 양수이면 첫 번째 횟수가 더 크고, 음수이면 두 번째 횟수가 더 크다.

> 정리일: 26.11.08 (Git 기록 기준)

```java
int balance = 0;
balance++; // 첫 번째 종류: 차이 1
balance--; // 두 번째 종류: 차이 0, 두 횟수가 같음
```

차이가 0이라는 정보만으로 각 종류가 몇 개였는지는 알 수 없다.
두 횟수 자체가 필요한 문제에서는 각각의 카운트도 유지해야 한다.

### 대상별로 차이 비교하기

> 정리일: 26.11.09 (Git 기록 기준)

비교 기준이 `보낸 횟수 - 받은 횟수`라면 보낸 횟수만으로 대상을 비교해서는 안 된다.
각 대상에 대해 차이를 구한 뒤 그 결과끼리 비교한다.

| 대상 | 보낸 횟수 | 받은 횟수 | 차이 |
| --- | ---: | ---: | ---: |
| A | 3 | 3 | 0 |
| B | 1 | 1 | 0 |

A가 더 많이 보냈어도 차이는 둘 다 0이므로 이 기준에서는 동률이다.
각 횟수를 따로 저장한 뒤 빼거나, 기록을 읽을 때 보낸 대상의 차이에 1을 더하고
받은 대상의 차이에서 1을 빼는 방식으로 계산할 수 있다.

## 구간이 시작될 때 개수 세기

> 정리일: 26.11.08 (Git 기록 기준)

입력을 연속된 구간으로 나누고 모든 문자가 정확히 한 구간에 포함되며,
끝에 남은 미완성 구간도 한 개로 인정한다면 구간의 시작 시점에 개수를 셀 수 있다.

1. 새 구간의 첫 문자를 읽을 때 개수를 1 증가시키고 그 구간의 기준 문자를 정한다.
2. 문자를 읽으며 기준 문자와 같은 문자에는 1을 더하고, 다른 문자에는 1을 뺀다.
3. 차이가 0이 되어 구간이 끝나면, 다음 문자가 있을 때 새 구간을 시작한다.

이 방식에서는 첫 문자가 항상 기준 문자와 같으므로 새 구간을 시작한 직후 차이는 1이다.
입력을 다 읽은 뒤 다음 문자가 없다면 새 구간도 시작하지 않는다.

예를 들어 `"pqp"`를 위 규칙으로 읽는 과정은 다음과 같다.

| 현재 문자 | 동작 | 처리 후 차이 | 구간 개수 |
| --- | --- | ---: | ---: |
| 첫 `p` | 새 구간 시작, 기준과 같음 | 1 | 1 |
| `q` | 기준과 다름, 두 횟수가 같아져 구간 종료 | 0 | 1 |
| 마지막 `p` | 새 구간 시작, 기준과 같음 | 1 | 2 |

마지막 구간은 종료 조건을 만족하지 못했지만 시작할 때 이미 개수에 포함됐다.
따라서 이 방식에 마지막 구간을 세는 증가 연산을 다시 추가하면 중복 집계가 된다.
종료 조건을 만족한 구간만 인정하는 문제라면 같은 방식으로 세어서는 안 된다.

## 반복문과 재귀의 처리 비용

> 정리일: 26.11.08 (Git 기록 기준)

각 문자를 한 번씩 읽고 상수 시간의 연산만 하면 시간 복잡도는 `O(n)`이다.
기준 문자, 차이, 구간 개수 등 고정된 수의 변수만 쓰면 추가 공간은 `O(1)`이다.

재귀도 각 문자를 한 번만 처리하면 시간은 `O(n)`일 수 있지만, 호출 깊이에 따른 스택 공간이 든다.
반복문으로 순차 처리하면 하위 호출에 맡긴 부분을 다시 순회하는 제어 흐름도 피할 수 있다.
재귀의 처리 범위는 [반환값과 재귀 호출](../java/recursion-and-return.md)을 참고한다.
